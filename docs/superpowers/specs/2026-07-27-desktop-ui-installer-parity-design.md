# Desktop UI, Installer, and Updater Parity Design

## Goal

Ship version `2.2.2` so the Electron desktop application and Windows installer
contain the same current production React UI generated by the repository build,
while preserving the existing visual system and safe signed-update boundary.

## Context and evidence

- The checked-in installer is `Rempeyek-Agent-OS-Setup-2.2.1.exe`, created on
  2026-07-26, while user-facing source commits exist from 2026-07-27.
- Electron serves `apps/web/dist` through the owned local server. A stale `dist`
  folder therefore produces a stale desktop UI even when the source UI is newer.
- The current production build is already code-split: the entry bundle is
  290.7 kB (92.6 kB gzip) and `AgentMapView` is lazy-loaded at 119.0 kB
  (39.8 kB gzip). No bundle split will be added without a measured regression.
- The updater service already checks on launch and every six hours, downloads
  only when the user setting permits it, waits for an approved restart, blocks
  restart during lifecycle work, and hides raw updater errors.

## Scope

### Included

1. Make every desktop development, package, and distribution command build the
   web renderer before Electron consumes it.
2. Add a deterministic packaged-renderer parity test: the packaged
   `app-root/apps/web/dist` must contain the same index entry and referenced
   assets as the source build used for the package.
3. Bump root, web, and desktop package versions to `2.2.2`, regenerate the
   lockfile, and update the local installer handoff documentation.
4. Build fresh NSIS and portable Windows artifacts and verify package contents,
   asset parity, installer metadata, and the existing updater state machine.
5. Preserve the current visual tokens, themes, navigation, accessibility
   behaviors, lazy `AgentMapView` boundary, and safe updater messaging.

### Excluded

- No UI redesign, new desktop navigation, color/type changes, or unmeasured
  performance refactor.
- No weakening of update verification, no unsigned stable feed, and no release
  publication, tag, push, or deployment.
- No changes to the pre-existing public-release test failure caused by
  owner-specific paths in `checkpoint.md` and an existing plan document.

## Architecture

The root desktop scripts become the one supported entry point for desktop
development and packaging. Each first runs the existing Vite production build,
then invokes Electron or electron-builder. Electron continues to load the owned
loopback server, and that server continues to serve the generated `dist` files.
This preserves one renderer implementation for root development, Electron
development, and installed packages.

The package test reads the built web `index.html`, collects local `/assets/...`
references, and compares their bytes with the same paths under the unpacked
Electron resources. A package can no longer pass while embedding a previous
renderer build.

The updater remains intentionally fail-closed. Direct user auto-update becomes
available only after the existing signed-tag workflow receives a trusted
`CSC_LINK`, `CSC_KEY_PASSWORD`, and `DESKTOP_PUBLISHER_SUBJECT`, produces valid
Authenticode signatures, and publishes the exact `latest.yml` plus installer
to the GitHub Release for tag `v2.2.2`. Local work verifies that this release
contract is ready; it cannot substitute for the external signing and publishing
authority.

## User experience and performance guardrails

- Desktop must display the exact current React UI and all existing themes.
- Existing loading skeletons, focus behavior, reduced-motion support, and
  `AgentMapView` lazy loading remain unchanged.
- Packaging may not increase the measured renderer entry or lazy-map bundle
  sizes unless an accompanying test documents a necessary user-visible change.
- The installer continues to preserve user data and must not embed vault,
  telemetry, credentials, plans, checkpoints, or owner-specific paths.

## Verification

1. Run the new focused parity test red before changing the scripts.
2. Run `npm run desktop:dev` after a source-only sentinel change in a temporary
   test fixture or test-controlled build directory to prove it builds first.
3. Run `npm run build`, `npm run test:desktop`, `npm run desktop:dist`, and
   `npm run desktop:test-package`.
4. Confirm the NSIS and portable names contain `2.2.2`, the unpacked app has
   the exact current `dist` entry/assets, and `latest.yml` SHA-512 references
   the produced installer.
5. Run the updater unit tests for available, downloaded, lifecycle-blocked,
   missing-metadata, and redacted-error states.
6. Run `npm run audit:public`, `git diff --check`, and `graphify update .`.

## External release acceptance boundary

The new artifacts are locally verified release candidates only. A direct
end-user auto-update claim requires all of the following independent evidence:

1. A trusted Authenticode signature on the installer and portable executable.
2. A GitHub Release tagged `v2.2.2` with the signed NSIS installer, blockmap,
   and generated `latest.yml` whose SHA-512 matches the uploaded installer.
3. A clean-machine install, update discovery, background download, approved
   restart, and post-update launch test.

Without these external steps, the UI and installer synchronization is complete
locally but the updater correctly reports no verified public update.

## Self-review

- Scope maps to renderer freshness, installer rebuild, measured performance,
  and updater readiness only.
- No placeholder requirements or unbounded redesign work remain.
- The version and updater contracts use the same `2.2.2` identifier throughout.
